# Polyvise: guided decision workspace

This iteration prioritizes helping a new visitor understand what to ask, which mode to choose, what will happen, and what they can take away. It also tightens the boundary between the shared engine and the products that use it.

## What changed

- Compact editorial introduction and a two-column question workspace, stacking on mobile.
- Goal-based mode choices: make a decision, find common ground, explore a strategy.
- Context next to the question; relevant examples update with the selected mode.
- Participant schematic, expected outputs, steps and expandable rules.
- Native radio controls, keyboard focus, character limits, explicit errors and duplicate-submission protection.
- Settings reflect actual core routing, including the difference between duo and quartet. Request serialization omits inactive options.
- Mode guide links preselect the correct mode.
- An interactive, explicitly illustrative example explains three outputs from the same question without a provider call.
- Completed debates offer a clear path to the verdict. All completed modes can download a Markdown brief with sources.
- In-flight consensus and panel runs have their own status view rather than a misleading debate shell.
- Simulated local results are labeled in the interface and exports.
- A concise architecture disclosure makes the separation of product and engine inspectable.
- Core now uses neutral advocate roles and presentation language. Debatefrog owns its character voice, reading level, round labels, and green/pink presentation rules.
- Core framing is mode-aware: debate mode receives a formal resolution, while Consensus and Advisory Panel preserve the user's open question.

## Actual model routing in core 0.4.0

| Mode | Model choices that affect calls |
| --- | --- |
| Debate, duo | Pro, con, judge. Each side builds its own claims and turns. |
| Debate, quartet | Quick for scouts, opening, questions and closing; deep for claims and rebuttals; judge for review, scorecard and summary. Both sides are batched by round. |
| Consensus | Quick for lens creation; deep for each agent's positions; judge for the summary. |
| Advisory panel | Deep for each advisor; judge for the chair. No quick-model call. |

Regression tests record actual calls from each engine and compare the roles to the exposed controls. This prevents settings that look meaningful but have no effect.

## Verification

- A live duo debate on polyvise.ai completed in roughly 31 seconds.
- Local browser checks: consensus with 3 perspectives and 2 rounds, advisory panel, debate, mode-link preselection, native keyboard selection, example switching, and responsive layouts.
- Local execution uses deterministic providers and mock evidence; these checks verify interaction and integration, not live model quality.
- Polyvise: 32 unit/integration tests, typechecking, and production build.
- Polyvise Core: 67 tests, typechecking, and package build.
- Debatefrog: 9 tests, typechecking, and production build against the refactored local core package.

## Focus for the next iteration

Live provider quality should be evaluated separately across all three modes before production rollout. In particular, audit generic deterministic opening positions in duo runs and ensure missing outputs never appear to establish real agreement.

The coordinated core change was tested through a local package tarball. Publishing and deployment should update consumers through the normal restricted-registry release flow rather than committing a sibling-repository file dependency.

The source repositories use a restricted package registry. The architecture links are accurate destinations, but repository visibility should be checked before relying on them as an employer-facing code sample.
